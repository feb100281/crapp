# COSMORELAX

Управленческий дашборд на Django + Unfold + Tailwind.

## Структура

```
config/         настройки, Unfold, urls
core/           общие вещи проекта
  admins/       UI-кит админки (бэйджи, ячейки, базовый ModelAdmin)
  admin/        регистрация моделей core (Jobs)
  models/       Jobs — список команд, запускаемых из админки
  management/   сами команды (bs, init_cp, oneass, run_job)
cp/             контрагенты: модель, админка, парсер-сервисы
sql/            SQL для duckdb
data/parquet/   промежуточные снапшоты
```

## Контрагенты (`cp`)

Модель `CP` — справочник контрагентов. Источник данных — DaData
(`findById/party`), ключ берётся из `.env` (`DADATA_API_KEY`).
Полный ответ источника хранится в `payload`, банковские счета из выписок —
в `ba`.

Админка (`cp/admin.py`):

- список — визитка контрагента (аватар, название, ИНН/ОГРН), бэйдж статуса,
  география, руководитель, выпадающий список счетов, бэйдж актуальности
  (зелёный до 60 дней, жёлтый до 180, красный дальше);
- фильтры — по названию, ИНН/ОГРН, руководителю, статусу, стране, региону,
  актуальности данных и наличию счетов; применяются кнопкой;
- карточка — вкладки «Контрагент» / «Реквизиты» / «DaData»; на вкладке
  DaData сырой `payload` показан читаемой карточкой + JSON-редактор;
- ИНН у сохранённой записи только для чтения — это ключ связи с источниками.

### Обновление данных

| Где | Что делает |
|-----|------------|
| Кнопка «Обновить» в строке списка | тянет DaData по одному контрагенту |
| Кнопка «Обновить из DaData» в карточке | то же, с возвратом в карточку |
| Массовое действие в списке | до 300 записей за раз, с троттлингом |
| Команда `init_cp` | полная загрузка: DaData → parquet → модель |

Пустые значения источника существующие данные не затирают.

## Банковские выписки (`bs`)

Команда `bs` разбирает выгрузки 1CClientBankExchange из папки, пишет два jsonl
(`data/json/banks/bank_accounts.jsonl`, `data/json/bs/bs.jsonl`) и делает из них parquet
через `sql/bs/statements.sql` и `sql/bs/bs.sql`.

### Идентификаторы

Ключи считаются по содержимому, а не по имени файла — одна и та же выписка,
положенная в папку дважды под разными именами, получит те же id:

- `id` выписки = хэш(`РасчСчет` + `ДатаНачала` + `ДатаКонца`);
  если номера счёта в файле нет — откат на имя файла;
- `doc_id` операции = хэш(счёт выписки + тип + номер + дата + сумма + счета сторон + назначение).

Счёт выписки (`ba_number`) в ключе операции принципиален: внутренний перевод между
своими счетами попадает в две выписки — списание в одной, поступление в другой.
Это две разные строки, и склеивать их нельзя. Номер выписки в ключ операции, наоборот,
не входит: один и тот же платёж из двух выгрузок одного счёта за разные периоды —
одна операция.

Дополнительно пишутся `file_hash` (sha1 содержимого файла) и `source_file` — видно,
откуда строка и какие файлы буквально одинаковые.

### Дедупликация

Повторы не выбрасываются при разборе — они схлопываются в SQL
(`QUALIFY row_number() OVER (PARTITION BY id / doc_id ...) = 1`), а в лог задачи
пишется, какие файлы и выписки задвоились и сколько строк схлопнулось.

Документы привязываются к последней прочитанной секции `СекцияРасчСчет` — если в
файле несколько счетов, а документы идут общим списком в конце, все они уйдут на
последний счёт. Для стандартных выгрузок (один счёт на файл) это ровно то, что нужно.

Менять только SQL нельзя: новые колонки появляются только после повторного разбора,
поэтому задача `bs` всегда делает оба шага подряд.

## Команда `init_cp`

Два этапа:

1. **DaData → parquet.** Собирает уникальные ИНН из `data/parquet/bs/bs.parquet`,
   опрашивает DaData (≈5 запросов/сек, ретраи на 429/5xx) и складывает сырые
   ответы в `data/parquet/cps/init_cp.parquet`. Это долгий этап.
2. **parquet → модель.** Прогоняет `sql/bs/cp_init.sql` через duckdb
   (разбор payload, нормализация названия, сбор счетов) и обновляет `CP`
   через `bulk_create` / `bulk_update`.

Параметры задачи (`Jobs.param`), все необязательные:

```json
{
    "dadata_api_key": "...",
    "skip_fetch": true,
    "skip_load": true,
    "limit": 100
}
```

- `dadata_api_key` — переопределяет ключ из `.env`;
- `skip_fetch` — не ходить в DaData, обновить модель из готового снапшота
  (то, что нужно, когда парсить 20 минут заново не хочется);
- `skip_load` — только спарсить, модель не трогать;
- `limit` — ограничить число ИНН, для проверки.

## UI-кит админки (`core/admins`)

- `AppModelAdmin` — базовый класс: широкие списки, фильтры с кнопкой,
  JSON-редактор, предупреждение о несохранённой форме;
- `Badge` / `TimeBadge` / `ChoiceBadge` — бэйджи для `@display`;
- `FirstCol` / `Stack` — визитка и многострочные ячейки.

Вся вёрстка — семантические классы `pk-*` из `static/css/input.css`,
никакого инлайнового Tailwind внутри Python.

## Tailwind

См. `TAILWIND.md`. После правок `static/css/input.css`:

```bash
npx @tailwindcss/cli -i ./static/css/input.css -o ./static/css/output.css --minify
```
